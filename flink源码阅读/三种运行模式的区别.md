# Yarn三种运行模式区别

## 前言

我们先将一个并不严谨的结论写在前面，以便大家有一个感性的认识，以及可以更方便的阅读源码。

1. per-job模式作为最原始的模式，先后执行顺序为：
    1. [client] dag转化为StreamGraph，再转化为JobGraph
    2. [client] 申请创建集群，启动AppMaster
    3. [remote] JM将JobGraph转化为ExecutionGraph
    4. [remote] 申请TM，将ExecutionGraph调度到TM上执行
2. application模式：
    1. [client] 申请创建集群，启动AppMaster
    2. [remote] dag转化为StreamGraph，再转化为JobGraph
    3. [remote] 本地提交，上传JobGraph到BlobServer，各种依赖jar
    4. [remote] JM将JobGraph转化为ExecutionGraph
    5. [remote] 申请TM，将ExecutionGraph调度到TM上执行
3. session模式：
    1. [client 1] 申请创建集群，启动AppMaster
    2. [client 2] dag转化为StreamGraph，再转化为JobGraph
    3. [client 2] http请求，向集群提交任务
    4. [remote] 加载JobGraph, JM将JobGraph转化为ExecutionGraph
    5. [remote] JM调度任务

下面我们分别从源码的角度，详细剖析这三种模式的JM启动流程

## 分析

per-job模式的入口类是YarnJobClusterEntrypoint。application模式的入口类是YarnApplicationClusterEntryPoint。session模式的入口类是YarnSessionClusterEntrypoint，我们看他们的main方法，可以看到主流程基本一致，唯一的区别在于创建XXXClusterEntryPoint实例的时候，是分别创建了三个不同的实例。

从ClusterEntrypoint#runClusterEntrypoint看进去，依次调用

```
ClusterEntrypoint#startCluster 
-> ClusterEntrypoint#runCluster 
-> createDispatcherResourceManagerComponentFactory
```

这是一个抽象方法，我们可以看到YarnJobClusterEntrypoint和YarnSessionClusterEntrypoint都分别实现了这个方法，而YarnApplicationClusterEntryPoint的实现是在其父类ApplicationClusterEntryPoint中。

createDispatcherResourceManagerComponentFactory这个方法返回一个DispatcherResourceManagerComponentFactory类型。该接口只有一个实现类DefaultDispatcherResourceManagerComponentFactory，内部包含三个成员变量，分别是创建DispatcherRunner、ResourceManager和WebMonitorEndpoint的工厂。定义如下：

DefaultDispatcherResourceManagerComponentFactory
  
  - DispatcherRunnerFactory dispatcherRunnerFactory;
  - ResourceManagerFactory<?> resourceManagerFactory;
  - RestEndpointFactory<?> restEndpointFactory;

三种模式对应ClusterEntrypoint的三个子类，各自根据其自身逻辑，返回对应组件的子类。具体区分如下（缩进代表引用深度）：
  
**session**

- dispatcherRunnerFactory: DefaultDispatcherRunnerFactory
    - dispatcherLeaderProcessFactoryFactory: SessionDispatcherLeaderProcessFactoryFactory
        - dispatcherFactory: SessionDispatcherFactory
- resourceManagerFactory: YarnResourceManagerFactory
- restEndpointFactory: SessionRestEndpointFactory
  
**per-job**

- dispatcherRunnerFactory: DefaultDispatcherRunnerFactory
    - dispatcherLeaderProcessFactoryFactory: JobDispatcherLeaderProcessFactoryFactory
        - jobGraphRetriever: JobGraphRetriever
- resourceManagerFactory: YarnResourceManagerFactory
- restEndpointFactory: JobRestEndpointFactory
  
**application**

- dispatcherRunnerFactory: DefaultDispatcherRunnerFactory
    - dispatcherLeaderProcessFactoryFactory: ApplicationDispatcherLeaderProcessFactoryFactory
        - configuration: Configuration
        - dispatcherFactory: SessionDispatcherFactory
        - program: PackagedProgram
- resourceManagerFactory: YarnResourceManagerFactory
- restEndpointFactory: JobRestEndpointFactory

下面我们从各组件角度结合组件初始化流程详细说下他们之间的区别，顺序从简单到复杂。

### WebMonitorEndpoint

per-job和application模式都是用的JobRestEndpointFactory，该工厂创建MiniDispatcherRestEndpoint类型的WebMonitorEndpoint，所有实现也都在WebMonitorEndpoint中定义。而session用的SessionRestEndpointFactory，生成DispatcherRestEndpoint。

WebMonitorEndpoint和DispatcherRestEndpoint的主要区别就在于，per-job和application在提交过程是直接提交任务，能获取到JobGraph，而session是先创建集群，在由外部client通过rest接口提交任务，因此，session模式下的WebMonitorEndpoint需要额外增加一个处理JobSubmission请求的接口。JobSubmitHandler负责处理该请求，并将请求转化成Dispatcher可识别的任务提交，调用DispatcherGateway#submitJob方法提交任务。

### ResourceManager

由于都是运行在yarn上的模式，故资源管理器工厂用的都是YarnResourceManagerFactory，此处没有差异，不做赘述

### DispatcherRunner

三种模式在DispatcherRunner上差异较大，这里详细研究一下。我们将从以下三个类为入口，详细介绍三种模式的DispatcherRunner的区别

- SessionDispatcherLeaderProcessFactoryFactory
- JobDispatcherLeaderProcessFactoryFactory
- ApplicationDispatcherLeaderProcessFactoryFactory

公共入口在DefaultDispatcherResourceManagerComponentFactory#create中，调用DefaultDispatcherRunnerFactory#createDispatcherRunner创建DispatcherRunner组件，在createDispatcherRunner中，会调用DispatcherLeaderProcessFactoryFactory#createFactory方法，这里根据构造DefaultDispatcherRunnerFactory时传入的不同参数，分别执行其子类的createFactory方法，即上述三个子类，下面详细介绍

#### SessionDispatcherLeaderProcessFactoryFactory

该子类在createFactory中创建SessionDispatcherLeaderProcessFactory类型实例。

该工厂的#create创建方法在DispatcherRunner选主成功后调用，创建SessionDispatcherLeaderProcess对象并执行其父类的start方法。

其内部会先尝试获取需要恢复的任务的JobGraph，并调用SessionDispatcherFactory创建一个StandaloneDispatcher实例并启动，托管在DefaultDispatcherGatewayService中。

调用链如下：

```
DefaultDispatcherResourceManagerComponentFactory#create
-> DefaultDispatcherRunnerFactory#createDispatcherRunner
-> SessionDispatcherLeaderProcessFactoryFactory#createFactory
-> 异步选主

选主成功后
DefaultDispatcherRunner#grantLeadership
-> DefaultDispatcherRunner#startNewDispatcherLeaderProcess
-> DefaultDispatcherRunner#createNewDispatcherLeaderProcess
-> SessionDispatcherLeaderProcessFactory#create

异步调用
AbstractDispatcherLeaderProcess#start
-> startInternal
-> SessionDispatcherLeaderProcess#onStart
-> SessionDispatcherLeaderProcess#createDispatcherIfRunning
-> SessionDispatcherLeaderProcess#createDispatcher
-> DefaultDispatcherGatewayServiceFactory#create
-> SessionDispatcherFactory#createDispatcher
-> Dispatcher#onStart
```

整个启动过程除了尝试恢复作业，并没有看到有JobGraph的出现，即当前Dispatcher处于空跑状态。

#### JobDispatcherLeaderProcessFactoryFactory

该子类参与的逻辑如下

1. 首先通过JobGraphRetriever获取到提交的JobGraph，JobGraphRetriever的实际子类是FileJobGraphRetriever，在YarnJobClusterEntrypoint创建DefaultDispatcherResourceManagerComponentFactory的时候根据Configuration构造的，能够根据Configuration中的internal.jobgraph-path配置，读取到JobGraph的二进制文件
2. 将JobGraph包含在JobDispatcherLeaderProcessFactory中，返回JobDispatcherLeaderProcessFactory的实例
3. 接着重复上述选主流程，选主成功后，调用JobDispatcherLeaderProcessFactory#create
4. 接着异步调用JobDispatcherLeaderProcess#onStart方法
5. 调用DefaultDispatcherGatewayServiceFactory#create，传入JobGraph
6. 调用JobDispatcherFactory#createDispatcher，传入JobGraph
7. 创建MiniDispatcher，并调用start，底层调用Dispatcher#onStart
8. 由于附带JobGraph，onStart会基于JobGraph去启动任务

调用链如下

```
DefaultDispatcherResourceManagerComponentFactory#create
-> DefaultDispatcherRunnerFactory#createDispatcherRunner
-> JobDispatcherLeaderProcessFactoryFactory#createFactory
-> 异步选主

选主成功后
DefaultDispatcherRunner#grantLeadership
-> DefaultDispatcherRunner#startNewDispatcherLeaderProcess
-> DefaultDispatcherRunner#createNewDispatcherLeaderProcess
-> JobDispatcherLeaderProcessFactory#create

异步调用
AbstractDispatcherLeaderProcess#start
-> startInternal
-> JobDispatcherLeaderProcess#onStart
-> DefaultDispatcherGatewayServiceFactory#create
-> JobDispatcherFactory#createDispatcher
-> Dispatcher#onStart
-> Dispatcher#startRecoveredJobs
-> Dispatcher#runRecoveredJob
-> Dispatcher#runJob
```

#### ApplicationDispatcherLeaderProcessFactoryFactory

该子类参与的流程如下

1. 首先创建一个ApplicationDispatcherGatewayServiceFactory对象，该对象持有PackagedProgram，和一个SessionDispatcherFactory，接着以ApplicationDispatcherGatewayServiceFactory为参数创建SessionDispatcherLeaderProcessFactory并返回
2. 接着重复上述选主流程，选主成功后，调用SessionDispatcherLeaderProcessFactory#create
3. 接着异步调用SessionDispatcherLeaderProcess#onStart
4. 底层调用了ApplicationDispatcherGatewayServiceFactory#create，在该方法中调用SessionDispatcherFactory#createDispatcher创建StandaloneDispatcher对象。调用过程中定制了DispatcherBootstrapFactory类型参数的逻辑，同时JobGraph参数为空
5. Dispatcher在创建后调用start方法，底层回调onStart方法，根据JobGraph启动的逻辑执行后（由于传入空集合，这里是空操作），执行DispatcherBootstrapFactory#create方法，该方法创建ApplicationDispatcherBootstrap实例
6. ApplicationDispatcherBootstrap在创建过程中，传入PackagedProgram和DispatcherGateway（用于和Dispatcher交互），并调用其fixJobIdAndRunApplicationAsync方法，用于异步将作业提交到Dispatcher上

调用链如下：

```
DefaultDispatcherResourceManagerComponentFactory#create
-> DefaultDispatcherRunnerFactory#createDispatcherRunner
-> ApplicationDispatcherLeaderProcessFactoryFactory#createFactory
-> 异步选主

选主成功后
DefaultDispatcherRunner#grantLeadership
-> DefaultDispatcherRunner#startNewDispatcherLeaderProcess
-> DefaultDispatcherRunner#createNewDispatcherLeaderProcess
-> SessionDispatcherLeaderProcessFactory#create

异步调用
AbstractDispatcherLeaderProcess#start
-> startInternal
-> SessionDispatcherLeaderProcess#onStart
-> SessionDispatcherLeaderProcess#createDispatcherIfRunning
-> SessionDispatcherLeaderProcess#createDispatcher
-> ApplicationDispatcherGatewayServiceFactory#create
-> SessionDispatcherFactory#createDispatcher
-> Dispatcher#onStart
-> DispatcherBootstrapFactory#create
-> ApplicationDispatcherBootstrap<cinit>
-> ApplicationDispatcherBootstrap#fixJobIdAndRunApplicationAsync
-> ApplicationDispatcherBootstrap#runApplicationAsync       
-> ApplicationDispatcherBootstrap#runApplicationEntryPoint（异步）
-> ClientUtils#executeProgram //第一个参数为EmbeddedExecutorServiceLoader类型用于向Dispatcher提交任务
-> 然后走应用main方法
-> StreamContextEnvironment#execute
-> StreamContextEnvironment#executeAsync
-> EmbeddedExecutorFactory#getExecutor
-> EmbeddedExecutor#execute
-> EmbeddedExecutor#submitAndGetJobClientFuture //转换JobGraph
-> EmbeddedExecutor#submitJob
-> Dispatcher#submitJob
```
application模式引入了一个ApplicationDispatcherBootstrap的东西，用于将per-job模式下本该在client端执行的调用程序main方法和将DAG转换成JobGraph的工作放到了这里。

### 关于PipelineExecutor和PipelineExecutorServiceLoader

到这里集群启动过程以及任务提交流程在三中模式之间的差异就介绍完了。
现在我们了解从client端发起请求，到一个集群启动起来，运行我们提供的任务整个过程。我们再额外聊一聊在提交任务过程中不可缺少的两个组件PipelineExecutor和PipelineExecutorServiceLoader。

PipelineExecutorServiceLoader用来创建ExecutorFactory，该过程发生在StreamExecutionEnvironment调用execute执行任务的过程里面。不论什么模式，它最初的来源就是在调用ClientUtils.executeProgram时传进来的。

- 在session和per-job模式下，它的实现是DefaultExecutorServiceLoader，代码运行在client端，在调用getExecutorFactory方法时，根据提交时指定的模式和java spi机制选择加载哪种ExecutorFactory。
- 在application模式下，它的实现是EmbeddedExecutorServiceLoader，代码执行在远端集群上，在调用getExecutorFactory方法时，返回EmbeddedExecutorFactory，将JobGraph提交到Dispatcher上。

ExecutorFactory用于创建特定的Executor，不同模式对应不同的工厂类，创建不同的Executor，他们是实现将任务提交到集群的可扩展插件。
