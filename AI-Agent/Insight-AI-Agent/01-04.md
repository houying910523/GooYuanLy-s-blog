# 深入理解 AI Agent：设计原理与工程实战

## 一、AI Agent 入门

- 最小工程公式：`Agent = LLM + 上下文 + 工具`
- 完整工程组成：`Agent = Model + Harness`

### Harness

- Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
- Harness是Agent边界内，模型之外的运行与治理层

## 二、上下文工程

上下文是模型感知世界环境的全部信息，Agent 的下一步行动取决于截至当前的完整交互上下文。

### 上下文的构成

- System prompt：系统提示词。由开发者编写，定义 Agent 的身份、行为规则、约束条件。模型将其视为最高优先级的指令。整个对话过程中通常只有一条，放在消息列表的最前面。
- Tool Definitions：
- 对话轨迹：user + assistant + tool result + ...

Agent 框架的核心工作就是管理这个 messages 列表

### KV Cache友好的上下文设计

模型每生成一个 token，都要回头看一遍前文所有 token 的中间计算结果。为了降低成本（对模型提供商来说是计算成本，对用户则是真是的钱），KV Cache 的做法是：把前文的中间计算结果缓存下来，下一轮只需要计算新增 token 的部分。前提是要复用的上下文 token 前缀保持不变。若 token 序列从某个位置开始不同，首个不同 token 及其后的 KV 状态需要重新计算；此前位置的 KV 状态不受这次改动影响。

核心结论：

1. 系统提示词和工具定义一旦确定就不要改。
2. 动态信息永远追加到末尾——时间戳、用户状态等变化的内容，作为新消息追加到对话末尾，而不是修改已有的系统提示词。
3. 使用标准 API 格式，不要自行拼接消息。

### 提示词工程：优化系统提示词

优化维度：

1. 语气和风格
2. 结构化提示：使用xml标签包围块，使用markdown写细则
3. 流程驱动 or 规则堆砌
4. 业务规则细化：量化判断逻辑
5. few-shot示例：给模型看例子
6. 工具定义设计

### 渐进式披露

- skill 
- tools参数的按需获取

### Agent 状态栏

- **理论基础**：上下文学习更像是做检索而非推理，模型擅长从已有内容中查找信息，但不擅长主动归纳和总结。
- **状态栏的构成**：
  - 任务规划：引入TODO列表，放在消息列表末尾
  - 环境当前状态：包括系统时间、工作目录、工具调用次数
- **在消息列表中的位置**：放于消息列表末尾，使用xml标签包围
- **更新方式**：
  - 每轮替换：状态较大、更新频繁或轨迹很长时。它通常只使上次注入后的短后缀失效，同时避免陈旧状态持续累积
  - 持久追加：状态很小、两次更新间产生的消息很多，且会话长度受控时
此材料可能受版权保护。保留旧状态通常比反复重算长后缀便宜。（Claude Code使用此模式）。

几种好用的Agent状态栏技术：

1. 时间戳跟踪：将时间戳添加到每条用户消息和工具响应中
2. 工具调用计数器：维护一个全局字典，记录每个工具被调用的次数，并在响应中标注
3. TODO列表管理：`rewrite_todo_list` 和 `update_todo_status` 。每个 TODO 项包含唯一标识符、内容、状态（pending/in_progress/completed/cancelled）
4. 系统状态感知：注入当前时间、工作目录、操作系统类型、Shell 环境和 Python 版本等信息

### 上下文压缩

**为什么需要压缩：**

- 解决长度约束和成本约束
- 提升思考质量
- 缓解模型的上下文焦虑

**上下文学习的内部机制：检索而非推理** 

- 把需要思考才能得到的结论，变成可以直接检索的知识
- 不要让模型被动地在海量信息中检索，而要主动为模型提供经过提炼的结构化知识

**压缩对象**

1. System Prompt 和 Tool Definitions 永远不动——这是上下文最前面的“静态前缀”，KV Cache 持续缓存。
2. 压缩的对象是对话历史中的 tool results——当 Agent 框架用压缩后的摘要替换原始的工具输出时，替换位置之后的缓存会失效，但之前的缓存仍然有效。

**生产级的分层压缩机制**

1. 工具结果预算控制：大体积工具输出直接存磁盘，模型只看摘要预览。
2. 噪声直接删除
3. 归档式摘要：主轮做结构化摘要
4. 全量压缩：有LLM驱动的完整压缩，作为最后手段。

**压缩策略的设计原则**

1. 信息价值的非均匀分布：关键的决策点 > 支撑性的证据 > 冗余的噪声
2. 语义完整性
3. 任务相关性：压缩结果要保留和任务相关的信息，不同任务的压缩结果应该不同
4. 压缩即理解：有效的压缩需要深层的语义理解，因此负责压缩的模块本身要接近主模型的能力

**隔离优于压缩**

使用subagent将子任务上下文隔离，避免污染主agent上下文。

## 三、用户记忆与知识库

### 用户记忆系统

主要背景是为了让Agent实现跨会话提供个性化服务。

**用户记忆内容包括以下八项**

- 个人信息保留：记住用户身份等长期个人信息
- 偏好追踪：跟踪并记住用户的长期偏好
- 上下文切换：在多个话题之间切换时保持连贯
- 记忆更新：当用户提供与旧信息矛盾的新信息时能正确处理
- 多会话连续性：跨会话保持知识
- 复杂思考：基于多个记忆片段联合思考，例如当用户对花生过敏时推荐泰国菜应主动提醒注意花生成分
- 时间感知：记住日期、理解相对时间、进行时间计算
- 冲突解决：识别并处理记忆之间的不一致

**记忆能力分为三层**

1. 基础回忆 —— 这是记忆系统最根本的能力，要求 Agent 能够准确存储和检索用户直接提供的、结构化的、无歧义的信息。如 “我的会员号是 12345”，在后续需要时精确返回。这一层级确保了记忆系统的基本可靠性，是后续更复杂能力的基础。
2. 多会话检索 —— 要求 Agent 在面对来自不同对象、不同时期的多段会话时，能检索出所有相关信息并推理判断。真实世界的交互往往不是一次性完成的，而是通过不同客服渠道或在不同时间分别完成的。当拥有两辆车的用户要求“为我的车预约保养”时，系统需找出两辆车的全部信息，并主动询问需要为哪辆车提供服务，而不是随便猜一辆。询问贷款状态时需分辨正在履行的有效合同，忽略过去咨询但未生效的报价。取消 “洛杉矶之旅” 时需理解旅行是复合事件，主动关联所有相关预订“（机票和酒店）。
3. 主动服务 —— 这是衡量 Agent 是否达到“助理”水准的最高标准。它要求系统综合来自多个会话、甚至很久以前的信息，提供具有预见性的主动帮助，从看似无关的记忆中发现深层联系。预订国际航班时主动关联数月前存储的护照信息，发现即将过期并发出预警。手机损坏时主动整合所有保障方案（手机自带的保修、信用卡附加保修条款、运营商保险），为用户提供完整的解决方案选项列表。报税季主动从过去一年的记录中搜寻并整合所有税务文件（股票销售、自由职业收入、房产税），呈现完整待办清单。这种能力要求系统在没有明确指令的情况下，主动规避潜在问题和整合复杂信息。

**记忆的层次结构**

1. 轨迹：即Agent一次运行过程中的完整历史记录
2. 用户长期记忆：跨会话、跨实例的持久化存储，通常与用户ID绑定，以键值对形式存储。

**何时提取**

通常记忆提取不放在会话主流程中，而是等一段会话进行完成后，使用完整的会话记录在后台单独请求一次LLM，提取与用户有关的属性，包括各种静态属性（姓名、兴趣爱好等），以及各种主题形式的记忆（比如出行、工作等方面）。

可以针对每个会话单独提取，也可以对批量会话提取，提取后，在将现存的记忆一起丢给LLM做merge。

个人觉得应该对每个记忆都打上时间戳，这样在未来当出现内容冲突时能让模型更好的决策，或理解某一状态的变化。

**多类型记忆协同**

长期记忆的三种类型：

- **情景记忆（Episodic Memory）**：关于具体事件和经历的记忆。人类例子：“上周三和同事在那家意大利餐厅吃了一顿很棒的晚餐”。Agent 对应：前面订机票例子中的“用户订了下周五去东京的 ANA 航班”——记录了一个具体事件的时间、对象和细节。
- **语义记忆（Semantic Memory）**：从具体事件中抽象出的一般性知识。人类例子：“意大利的首都是罗马”。Agent 对应：“用户是素食者”、“用户偏好靠窗座位”——这些不是某次对话的记录，而是从多次交互中提炼出的稳定特征。
- **程序记忆（Procedural Memory）**：关于行为模式和流程的记忆。人类例子：骑自行车的能力。Agent 对应：从用户反复订机票的模式中学到的通用流程——“先搜索直飞航班→确认座位偏好→使用常旅客号码→订餐”。

除三类长期记忆外，参考架构还显式保留了工作记忆这一层，管理当前任务状态，与长期记忆动态交互——重要信息选择性转移到长期记忆，相关长期记忆被激活并加载到工作记忆。

## 工具

### 工具的分类

- 感知工具：agent主动调用，获取外部信息。如网页搜索，读取文件
- 执行工具：agent主动调用，改变外部世界。如执行代码，编辑文件
- 协作工具：agent主动调用，驱动其他agent或人类。如创建subagent，高危操作请求人类确认
- 用户沟通工具：agent主动调用，agent主动向用户传递信息
- 事件触发工具：外部世界驱动Agent行动

### 工具设计通用原则

- 通用工具优于专用工具，除非存在明确的安全、权限或性能理由
- 当需要：
  - 屏蔽平台差异
  - 嵌入安全、权限和审计检测逻辑
  - 参数过于复杂
- 复杂流程让代码来编排工具调用

### 工具描述的艺术

**工具描述的核心**

- 让 LLM 知道“什么时候用”，而不只是“能做什么
- 清晰列出工具的边界条件——做不到什么、不接受什么输入
- 参数描述应该用具体例子代替抽象规范
- 返回值也需要描述清楚，JSON格式返回值增加示例

### 工具太多的烦恼

当工具数量达到几十几百个，模型选择合适工具的准确率会下降，此时不应该一次性将所有工具提供给模型，应该让模型从被动选择转变为主动发现。

常见方案是：系统提示词中仅保留少数基础工具（bash，web_search等），外加一个工具搜索工具，Agent 用自然语言描述需求即可检索并加载。即“Agent 声明缺口、系统按需注入”

每次搜索到对应工具后，工具的描述和参数schema作为一个tool_call消息追加到消息列表中，后续保持不动。同时可以在Agent状态栏中记录当前agent可用的工具列表。
另外这个搜索功能会依赖工程上的离线构建，即提前将工具描述相关信息进行向量化并存储到向量数据库中，搜索工具根据模型传递给工具的自然语言进行检索召回。

### 各类工具的设计重点

#### **感知工具**

感知工具的挑战在于一次搜索可能返回数万字符，一是快速耗尽上下文，二是让有效内容淹没在噪声中。可使用如下手段进行优化：

- 上下文感知压缩，当要输出的内容过大时，提前单独调用一个LLM根据查询意图对内容进行压缩
- 搜索工具的返回格式与分页：针对返回结构化列表的搜索工具，可对列表进行分页，或提供一个cursor游标参数，并在返回结果中标注下一页的获取方式，由 Agent 自主决定是否继续翻页
- 读取类工具：提供offset/limit参数，按需读取大文件的指定片段。当内容超过阈值必须截断时，应明确标示截断情况：注明省略了多少内容、如何读取剩余部分
- 多模态感知
  - 使用支持多模态的模型
  - 将多模态能力抽象为工具，转换为文本描述

#### **执行工具**

执行工具设计重点在于安全约束

- 输入验证，独立模型对参数进行安全审查
- 自动验证与反馈闭环，比如write_file写入代码时，自动调用linter工具进行代码静态检查
- 长输出的阶段与持久化，只输出头尾部分，中间省略，并提供读取方式
- 执行环境隔离：沙箱

#### **协作工具**

当任务超出单个 Agent 的能力边界时，协作工具可以让它把子任务委托给其他 Agent 或人类，再整合各方的结果

子Agent的设计哲学：

- 角色定义要清晰：开门见山说明“你是专门负责 XXX 的助手 Agent
- 任务边界要明确界定。什么在职责范围内，什么需要转交或上报
